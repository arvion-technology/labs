The problem

A portal that is mostly server work.

A customer portal is read-heavy: dashboards, invoice lists, ticket threads, account settings. The interesting engineering is not the chrome, it is where the data is fetched, how much ships to the browser, and what happens on a slow connection.

The sample is built to show the Next.js answer to that: server components for reads, route handlers for mutations, and a static export so the whole thing can be inspected on GitHub Pages without a server.

What we built

Server first, client only where it pays.

  • Dashboard rendered as a server component with metrics computed on the server.
  • Invoices list and detail routes, with typed access through lib/ data modules.
  • Support tickets with a reply thread, using route handlers for the write path.
  • Account settings with a session mock and a shared layout.
  • Static export with relative asset paths, so the demo runs from a plain file server.

How it is put together

 ├─ settings/

lib/ typed data access and formatting
test/ node:test on the data and formatting layer
out/ static export, copied to demo/

Security and money

  • Reads happen on the server; only the components that need interaction are client components.
  • Route handlers validate input and return typed payloads, so the client never assembles business objects.
  • The static export is a real build artifact, not a mock; the demo is that artifact with relative paths.
  • Tests cover the data and formatting modules, the parts most likely to drift between server and client.
